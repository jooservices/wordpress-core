# Internationalisation

* Text domains: `joo-core` (core), `jooservices-content` (plugin), the theme slug (theme). `I18nModule` loads `languages/joo-core-<locale>.mo` (exact locale, then the language), the theme domain from `languages/` and the plugin loads its own.
* `make i18n` runs WP-CLI `make-pot` in Docker for core and plugin, copies the POT files, builds `*-vi.po` from the dictionary `languages/vi.json` (single source of the Vietnamese strings), compiles `*-vi.mo` with `msgfmt` and fails when a shipped string has no translation. `node tools/i18n.mjs --check` does the check only; it is part of `make test-tooling`. `LanguageTest`-style integration tests also assert that the dictionary covers the POT.
* JavaScript strings: `I18n\JsStrings::map()` is merged into the `i18n` map of `joo-config`; the runtime `t(key, fallback)` reads it. A unit test scans the JS sources for `t('key', ...)` calls and fails when a key is missing from the map.
* Language service `I18n\Languages`: `codes()`, `all()`, `default()`, `isMultilingual()`, `current()` (plugin, then the post tag, then the site locale, then the default), `locale()`; extend names and locales with `joo/i18n/locales`. It sets `lang` (and `dir="rtl"` for Arabic, Hebrew, Persian, Urdu) on `<html>`. With `i18n.switch_locale` on, core strings of a post render in the post language (only for installed languages).
* Built-in tagging (no plugin): `_joo_lang` is accepted only for configured languages; `_joo_translation_of` must point to another post of the same type and a different language that is not itself a translation. `I18n\Translations::forPost()` lists the published group (cached); trashing the root promotes the oldest translation. Admin: "Lang" column, filter and "Set language" bulk actions; REST fields `joo_lang` and `joo_translations`.
